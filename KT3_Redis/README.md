# КТ3_1 — задание 2. Сбой Redis Cluster

[Условие задания](screenshots/00_условие_КТ3_1.png) — смоделировать сбой в кластере из девяти узлов с двумя репликами на мастер и проследить восстановление.

`failover.py` создаёт временный кластер Redis на портах 5500–5508 (3 мастера, 6 реплик), записывает `f=888`, получает подтверждение от двух реплик, останавливает процесс мастера `5500` сигналом `SIGSTOP` и ждёт автоматического повышения одной из его реплик. Затем проверяет покрытие слотов, состояние `cluster_state:ok`, чтение значения и возвращает прежний мастер сигналом `SIGCONT`. После возврата он должен стать репликой нового мастера.

Запуск на Linux с установленными `redis-server` и `redis-cli`:

```bash
python3 KT3_Redis/failover.py
```

Опыт также запускается автоматически в [GitHub Actions](../.github/workflows/kt3_redis_failover.yml). [Запуск № 43871841490](https://github.com/breevasofa/23---11/actions/runs/43871841490) завершился успешно: все проверки сценария и три этапа сохранения кадров прошли.

[Новые кадры терминала до сбоя](screenshots/05_кластер_терминал.png), [после переключения](screenshots/07_сбой_терминал.png) и [после восстановления](screenshots/08_восстановление_терминал.png) сняты мной во время указанного запуска GitHub Actions. Они включены в [отчёт DOCX](Отчёт_КТ3_1_сбой_кластера.docx). Снимки `01`–`04` — ранее предоставленные пользователем материалы и в обновлённый отчёт не входят.

Проверка отказа основана на [документации Redis Cluster](https://redis.io/docs/latest/management/scaling/): после `cluster-node-timeout` недоступный мастер заменяется репликой. Redis использует асинхронную репликацию, поэтому `WAIT 2 5000` уменьшает риск потери именно проверочной записи, но не делает кластер строго консистентным.
